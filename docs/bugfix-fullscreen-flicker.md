# Bugfix 复盘:全屏动画闪烁(gostty 刷屏闪烁)

> 困扰时间:2026-05 首次报告 → 2026-07 根因修复。期间经历一次"假修复"、一次回归、
> 一个长期错误归因(带宽瓶颈论)。本文档记录完整排查过程与教训。

## 症状

运行全屏字符动画(如 [gostty](https://github.com/ashish0kumar/gostty))时屏幕剧烈闪烁;
**只有大窗口时复现**,窗口缩小后消失;闪烁频率随系统负载波动,时好时坏。
Tabby(xterm.js + WebGL)在相同终端尺寸下不闪。

## 根因(逐层证据)

1. **ConPTY 拆帧**:gostty 每帧是一次 `write(ESC[2J + ESC[H + 全屏内容)`,但 ConPTY
   以自己的渲染节奏输出,把每一帧拆成两条管道写入:
   - 消息 1:裸 `ESC[2J`(4 字节,清屏)
   - 消息 2:~3.4KB 帧内容,**仅晚 1~3ms**(p50=1.3ms, p90=3.4ms)

   WS 消息日志实测:消息序列严格 `CECECE…` 交替(内容→擦除→内容),帧周期 ~35ms。

2. **直通链路放大问题**:当时的链路是 relay 每条管道读取立即转发一条 WS 消息 +
   `@xterm/addon-attach` 每条消息直接 `terminal.write()`。擦除和内容成为两次独立的
   write/解析/渲染。

3. **空白帧呈现**:xterm 在 1.3ms 的缝隙里把"擦除后、内容前"的中间态渲染并呈现了
   一个完整帧。CDP screencast 逐帧抓包:**大窗口下约 50% 的呈现帧是纯空白帧**,与
   内容帧交替 —— 这就是肉眼看到的"刷屏闪烁"。

4. **为什么只有大窗口**:终端尺寸小时 ConPTY 一帧不拆(擦除和内容合并输出),
   尺寸大、帧数据超过其内部阈值后才拆分。这解释了"小窗口不闪"的关键线索。

## 错误归因与假修复史(重要教训)

### 第一次修复(2026-05-26, `b20511f`)——有效,但有副作用

Rust 后端加 11ms 合批器(`recv_timeout(11ms)`)合并 ConPTY 拆分。**方向正确、当时
确实缓解了**,但 11ms 窗口让交互输入回显也能感到延迟,被认为是"不可接受的妥协"。

### 错误归因:带宽瓶颈论

当时在 SSH 带宽受限场景下观察到 Tabby 也闪烁,于是得出结论:"传输带宽/延迟是根本
原因,我们已经触碰到了传输瓶颈"。**这个结论只对了三分之一**:

- 带宽/延迟确实会**加剧**闪烁 —— 它拉大擦除和内容两条消息的时间间隔,使它们落入
  不同渲染帧的概率变大(Tabby 在慢 SSH 上闪烁是同一机制);
- 但本地场景带宽根本不是瓶颈,真正的机制是"**擦除和内容被渲染成了两帧**"这一
  竞争,带宽只是改变竞争概率的外部变量之一(窗口尺寸、系统负载也是)。

### 回归(2026-06-03, `c568f37`)——重构把修复删了

WebSocket 重构提交把后端的 batcher 当作旧 IPC 管线的附属品移除
("Removed: …, batcher threads"),并声称 "No user-facing changes"。
**实际上从那天起闪烁回归**,又过了一个多月才被真正定位。

教训:没有根因证据的缓解方案,其重要性不会被后来的维护者认识,重构时极易被误删。
缓解代码必须附带机制注释(为什么存在、删掉会发生什么)。

## 最终修复(2026-07-28, `7456a14`)

`src/terminal/batchattach.ts`(40 行,替代 `@xterm/addon-attach`):

```
WS message → 队列 → 6ms 定时器 → 合并为单个 Uint8Array → 一次 terminal.write()
                     队列 ≥128KB 立即刷新(保证洪流吞吐)
```

- 擦除+内容落入同一次解析与渲染,空白帧消除;
- 合并点在前端(最靠近渲染端),覆盖 ConPTY 拆帧、relay 16KB 分块、TCP 分段、
  WS 消息边界等**所有**拆分源,且 PTY/SSH/串口/demo 全链路受益;
- 代价仅输出侧 ≤6ms(旧方案 11ms 在后端),输入路径零改动;
- 验证:CDP screencast 逐帧分析,空白帧从 ~50% → 连续 3 轮(每轮 ~240 帧)为 0。

## 排查方法论(这次为什么能定位)

之前的排查失败在"看不见问题"。本次用了可量化的证据链:

1. **CDP 远程调试真实 WebView2**(`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=
   --remote-debugging-port`),注意要用独立 `WEBVIEW2_USER_DATA_FOLDER`,否则与
   运行中的实例共享浏览器进程,调试参数被静默忽略;
2. **`Page.startScreencast` 逐帧抓取**真实合成输出(静态截图会强制重合成,掩盖
   撕裂/空白帧;headless 环境无法复现 GPU 相关的时序问题);
3. **动画区域 bbox 追踪**作为空白帧判定指标(无亮点 = 空白帧),比肉眼/亮度均值
   更敏感;
4. **WS 消息内容日志**确认 4 字节消息就是裸 `ESC[2J`,并测出 1.3ms 的关键间隔。

## 遗留认知

- xterm 的 write→render 调度对"背靠背"消息的合并行为本身也有版本差异
  (6.0 vs Tabby 的 5.4),这解释了 Tabby 本地不闪的部分原因;但不要依赖这个差异,
  合批应该由我们自己保证。
- 正确的应用层方案是同步输出协议(DEC mode 2026, BSU/ESU)——应用显式声明帧边界,
  终端缓存到帧结束再渲染。gostty 这类老程序不用它,所以终端侧的合批兜底仍然必要。
- 排查期间顺带发现:CDP `setWindowBounds`/Win32 `SetWindowPos` 调整 OS 窗口后,
  WebView2 视口不跟随(800x600 冻结)——自动化测试大窗口的正确做法是
  `Emulation.setDeviceMetricsOverride` 强制页面视口。
